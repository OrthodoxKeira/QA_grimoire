# 🐛 Шаблон баг-репорта (Bug Report)

## Что такое баг-репорт?

Баг-репорт — это документ, описывающий **обнаруженный дефект** так, чтобы разработчик мог его воспроизвести и исправить.

**Хороший баг-репорт = быстрое исправление.** Плохой = долгое переписывание в трекере.

---

## Уровни серьёзности (Severity)

| Уровень      | Описание                                                              | Пример                              |
|----------------|----------------------------------------------------------------------------|------------------------------------------|
| 🔴 Blocker   | Система не работает, тестирование невозможно                          | Приложение не запускается           |
| 🟠 Critical  | Ключевая функция сломана, обходного пути нет                          | Нельзя оформить заказ               |
| 🟡 Major     | Важная функция работает некорректно, есть обходной путь               | Фильтр не работает, но поиск есть   |
| 🟢 Minor     | Функция работает, но с небольшими отклонениями                        | Неверный текст ошибки               |
| ⚪ Trivial   | Незначительный косметический дефект                                   | Опечатка, смещение на 1px           |

## Пример 2 — баг с частичной воспроизводимостью

### Метаданные

| Поле              | Значение                                                    |
|--------------------|------------------------------------------------------------------|
| **ID**            | BUG-104                                                     |
| **Название**      | Двойное списание при быстром повторном нажатии кнопки «Оплатить» |
| **Модуль**        | Оформление заказа / Оплата                                 |
| **Серьёзность**   | 🟠 Critical                                                 |
| **Приоритет**     | 🔴 Высокий                                                  |
| **Тип дефекта**   | Функциональный                                              |
| **Статус**        | Новый                                                       |
| **Автор**         | Мария Козлова                                               |
| **Дата**          | 2024-11-20                                                  |
| **Назначен на**   | Команда Payments                                            |

### Окружение

| Параметр       | Значение              |
|------------------|----------------------------|
| **Приложение** | ShopApp v2.6.0        |
| **ОС**         | macOS 14              |
| **Браузер**    | Safari 17.1           |
| **Устройство** | MacBook Pro            |
| **Окружение**  | Staging                |
| **URL**        | `https://staging.shop.com/checkout` |

### Описание

#### Шаги для воспроизведения

1. Добавить любой товар в корзину и перейти к оформлению заказа
2. Заполнить форму оплаты корректными тестовыми данными карты
3. Быстро дважды нажать кнопку «Оплатить» (интервал < 1 секунды)

#### Ожидаемый результат

Списание происходит один раз, повторное нажатие блокируется (кнопка становится disabled после первого клика).

#### Фактический результат

В части случаев создаются два отдельных заказа и происходит два списания средств.

### Дополнительно

| Поле                | Значение                                                       |
|-----------------------|-----------------------------------------------------------------------|
| **Воспроизводится** | Периодически (3 из 10 попыток)                                |
| **Регрессия**       | Не известно — раньше не тестировали такой сценарий             |
| **Связанные баги**  | Нет                                                            |
| **Связанные TC**    | TC-045                                                         |

**Вложения:** [video_double_charge.mp4]

> **Примечание:** это классический пример **race condition** — бага, который проявляется не всегда, а зависит от точного тайминга действий пользователя. Такие баги — одни из самых сложных для воспроизведения и требуют точного описания условий (в данном случае — скорости повторного клика).

## Советы

> **Название** должно отвечать на 3 вопроса: **Что сломано? Где? При каком условии?**
> Плохо: «Баг с ценой». Хорошо: «Цена не отображается на карточке товара».

> **Шаги воспроизведения** — пиши так, будто разработчик никогда не видел твоё приложение.

> **Не смешивай** несколько багов в одном репорте — один баг = один репорт.

> **Severity ≠ Priority.** Severity — насколько тяжело сломано технически. Priority — насколько срочно чинить бизнесу. Baг может быть Critical по серьёзности, но Low по приоритету (например, редкий edge case, который почти никто не встретит).

> **Проверяй воспроизводимость** — попробуй повторить баг несколько раз до отправки репорта. Если он всплывает не всегда — это важная информация для разработчика (возможна race condition, как в примере 2).
