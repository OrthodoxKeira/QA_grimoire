# Работа с требованиями

## 1. Требования в QA

**Требование** — это описание того, **что система должна делать**(функ) или **как хорошо она должна это делать**(нефунк)

QA работает с требованиями на двух уровнях:

**До тестирования** - читает требования и ищет в них проблемы. Баг найденный в требовании гораздо дешевле, чем найденный баг в разработке.

**Во время тестирования** - требования служат источником ожидаемого результата в тест-кейсах. Без них не понятно, что баг, а что - фича.


## 2. Виды требований

#### Бизнес-требования
    Увеличить конверсию в покупку
**Что хочет бизнес на верхнем уровне, обычно без деталей**

#### Пользовательские требования
    Хочу, чтобы был удобный поиск по сайт
**Какой продукт хочет конечный пользователь. User Stories**

#### Функциональные требования
    Строка поиска принимает до 100 символов. При вводе от 3 символов система показывает подсказки.
    Результаты поиска появляются не позднее 2 секунд.
**Конкретное поведение системы. Что именно система делает, при каких условия, с каким результатом**

#### Нефункциональные требования
    Страница результатов поиска загружается за <1 сек при нагрузке до 1000 пользователей
**Ограничения и характеристики качества**

## 3. На что обращать внимание. Проблемные места

1. Неизмеримость - не определенные\закрепленные атрибуты\параметры
    `Быстро, надежно, удобно, легко, качественно`
2. Неоднозначность - плавающие трактовки
    `Должен иметь возможность, нужный товар`
3. Неполнота - должны быть описаны все случаи, не только Happy path
    `При успешной оплате... (А в случае ошибки оплаты?)`
4. Противоречие - конфликтующие требования
    `Требование А противоречик требованию Б`
5. Нереализуемость - требование технически невозможно
    `Пользователь может оформить заказ на сайте даже без интернет соединения`

## 4. User Story

На практике требования могут оформляться в виде **User Story**. 

В формате `Как [КТО], я хочу [ЧТО], чтобы [ЦЕННОСТЬ]`

Пример User Story:
    `Как пользователь, я хочу найти товар по названию, чтобы не листать весь каталог`
    `Как пользователь, я хочу, чтобы после регистрации, я автоматически авторизовывался`

Однако User Story - это не требования для тестирования. К ней нужны **критерии приемки**.
Конкретные условия, при которых считается, что история реализована правильно.

Пример Acceptance Criteria:
    `* Строка поиска доступна на всех страница каталога`
    `* Поиск срабатывает от 3 введенных символов`
    `* После нажатия на кнопку "Регистрация", пользователь автоматически авторизуется в созданный аккаунт`

Такие критерии - источник тест-кейсов.

## 5. Чек-лист вопросов

Требование можно валидировать по следующему чек-листу

* Это можно измерить и проверить? -> Неизмеримость
* Все ли поймут это одинаково? -> Неоднозначность
* Что происходит, если что-то пойдет не так? -> Неполнота
* Не противоречит ли это другим требованиям? -> Противоречие
* Это вообще реализуемо? -> Нереализуемость
* Откуда берутся данные? Кто имеет доступ? -> Неполнота (данные и права)
* Что происходит на граничных значениях? -> Неполнота (граничные случаи)
