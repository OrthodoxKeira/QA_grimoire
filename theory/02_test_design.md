# Техники тест-дизайна


**Тест-дизайн** - процесс выбора **какие именно значения** тестировать, чтобы найти максимум багов при минимуме тестов.

`Всё протестировать невозможно - нужна система`

## Техники

### Классы эквивалентности (Equivalence Partitioning)

Разбиваем\объединяем входные данные для тестирования на классы.

`Напр. Допустимые значения, Ниже допустимых, Выше допустимых`

### Граничные значения (Boundary Value Analysis)

Зачастую баги живут на границах допустимых\не допустимых значений из-за ошибок в условиях (`> vs >=`)

`Напр. длина пароля должна быть 8-12 символов. Тестируем нижнюю границу (7 и 8) и верхнюю (12 и 13)`


### Граничные значения + Классы эквивалентности

Часто эти две техники используются в паре.

``Значение — Класс — Граница? — Ожидание``

### Тестирования на спецзначения

Отдельные значения, которые могут сломать систему.
* Ноль
* Отрицательные числа
* Очень большие числа
* Дробные числа
* Пустая строка
* Строки вместо чисел
* Спецсимволы (`!@#$`, эмодзи, иероглифы\кириллица)


### SQL-инъекции и безопасность
`' OR '1'='1`

Система может не экранировать ввод и такая строка может обойти авторизации или достать данные из БД.

### Попарное тестирование

Если система ожидает несколько параметров на ввод одновременно.
Проверяются все возможные комбинации пар значений для каждого параметра, вместо полного перебора.
Часто используются плагины для генераций пар.
